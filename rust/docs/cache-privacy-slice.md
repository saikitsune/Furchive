# Explicit cache privacy control

New Privacy section requires a fresh checked confirmation before Clear cached browsing data. Clearing closes results/viewer/thumbnails/suggestions and revokes the current Rust media generation/cursor/pool snapshot, then logically deletes discardable post/pool metadata through the DB actor. Saved searches, pins, settings, native account entries, downloads/active workers/history, original artwork and normalized sidecars are outside this action. No arbitrary root/path is accepted. Does not promise secure erasure: SQLite freelist/WAL/journal/backups, in-flight/decoded webview/OS buffers may retain bytes. Future explicit browsing may cache again.

A Rust async read/write boundary surrounds search/favorites/pool/viewer-step/media-prepare and current-page queue authorization. Clear takes exclusive ownership and drains admitted operations before ACK, then revokes media/cursor/snapshot and deletes the DB cache transactionally. Slow admitted work can delay clear; not hard cancellation. Separate DB actor cache epochs capture before provider await and reject stale publication after clear, including non-desktop callers. Failed transactional clear leaves DB rows/epoch unchanged; the current UI/media view remains conservatively closed and a failure notice requires deliberate retry. Download actors and account credentials are never stopped/deleted by clear.

Native compile manifest, main handler and bundled-main permission declare only clear_cache. UI prevents concurrent repeated clear and ignores old search/preview/media generations; explicit new browsing is disabled while clear awaits. New native restart campaign checks rendered confirmation/clear acknowledgment plus preserved saved search/pin/download rows, and host reads persistent SQLite counts after final clear while validating existing artwork/sidecar bytes and download history. Closed inventory30first+12restart; actual new nativeGUI remains UNRUN until exact candidate qualification.
